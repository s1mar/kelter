# Limitations

Everything we know kelter does badly or have not tested, with the numbers.

## Limitations

- JevBench's hard tier is the weak spot: accuracy 0.568, and the model is overconfident there (mean top probability 0.657). The two padding and long-context training rounds tried so far did not improve it; they are recorded in `docs/results.md`.
- Null recall is reported on two test sets. The corrected set was defined after looking at test diagnostics; the original set gives 0.960.
- The action rule is conservative and its thresholds were not tuned, so it defers most held-out questions. Requests with no provenance tags are treated as one `unknown` segment: the engine can still act on ordinary options, but never on one marked `destructive`. It acts only when one option is left in the 95% set and the evidence is admissible: the spans give the same answer alone, masking them changes it, and their provenance is allowed for that kind of option. One exception: for an option you mark `low_stakes`, the masking check is reported (`verifier.necessity`) but not required, so the engine can act on it when masking the evidence does not change the answer (`policy_table.json`). It defers when "none of the options" wins or no evidence is admissible, and escalates when the evidence is admissible but more than one option is left or untrusted text moved the answer too far. Treat `act` as a strong signal and `defer` as the default, not as a judgment that the answer is wrong. A looser rule that also acted on high confidence without evidence was tested and not shipped: it acted on 2,217 of 3,340 held-out questions at the same accuracy, but acted on planted text in 19 of 3,120 cases (`docs/results.md`).
- kelter trusts the provenance labels you supply. Text labelled `user` or `system` counts as trusted. Only options you mark `destructive` (in `verdict_classes`) are limited to user or system evidence and to a small budget of influence from untrusted text; other options can rest on tool output. So label text from tools, web pages, files and other models as `tool_output` or `retrieved_doc`, and mark every irreversible option `destructive`. When planted text naming a wrong option carries a trusted label, the evaluation tool, which uses each record's own threshold, has the default variant act on the wrong option in 4 of 3,120 test cases and lower-latency in 6 of 3,120 (`results/eval/engine_Q1base.json`, `results/eval/engine_E1base.json`). The server uses the stricter policy threshold on every request; with it the default variant does so in 0 of 3,120 (`results/eval/engine_Q1r1_policy.json`).
- The default variant needs a GPU. On a CPU the server runs it unquantized, and one answer took about eight minutes on a test machine (`results/e2e/2026-11-13.json`). The latency tool's int8 figure, 11.5 s for the four passes, is a measurement of a quantized copy that the server does not use. The lower-latency variant runs on a CPU: 6 to 44 s for two questions unquantized in our runs, and about 3 s per decision in the same int8 measurement.
- Calibration on JevBench's public tiers is worse than on our held-out data (ECE 0.038 to 0.124 by tier); the temperature was fitted on different kinds of text.
- Latency was measured on one laptop GPU shared with the desktop. The power mode of the earlier runs was noted by hand and is not stored in their results files; the balance-mode file records it. The figures in its highest power mode are the fastest it gets; in the balanced mode the default variant's decision takes 688 ms instead of 542 ms (`results/eval/latency_Q1_balance.json`). The lower-latency variant was measured in the highest mode only.
- The injection guarantee was tested on synthetic shell-gating and account-deletion items, not on real agent traces.
- The evidence spans come from the encoder, not from the Qwen model, so they show what the encoder relied on; the necessity check then measures whether masking them changes the Qwen model's answer (0.586 of e-SNLI answers change, against 0.362 for a random mask of the same size).
- JevBench's public tiers were used to choose between candidate models, each time under a rule written before the run (the default replaced the earlier ensemble partly on pooled public accuracy, 0.766 against 0.498). No public item was trained on, but the public-tier numbers are selected-on and should be read as optimistic. The sealed tier has never been seen.
- The server is stricter than the evaluation tool. Every request is given the `policy` type, so the engine uses the threshold fitted on policy questions (0.991) for all of them; the evaluation tool uses each test question's own type (0.455 to 0.991). Measured on the same held-out questions, the server's rule acts on 14% (475 of 3,340, all 475 correct) and escalates 15%; the evaluation tool's figures elsewhere in these documents are 26% and 3%. The `coverage_level` of 0.95 in an answer is therefore conservative for questions that are not policy questions (`results/eval/engine_Q1r1_policy.json`).
- `score` questions are not calibrated. The calibration data holds only `choice` and `noul` questions, so a score question is served at temperature 1 and its shortlist uses a threshold fitted on the other two types.
- Long inputs are cut. The default model reads at most 4,096 tokens of prompt; the encoder also keeps at most 96 tokens of the instructions and 48 tokens of each option. From 0.3.5 an answer reports a cut state in `verifier.truncated`. From 0.3.7 the same flag is also true when the encoder cut the instructions to 96 tokens or an option to 48 tokens. Earlier versions cut silently, and before 0.3.7 the flag did not cover the instruction and option cuts.
- An option named by a bare letter, a digit, "yes" or "no" is shown to the model by its description. Before 0.3.7 such an option with an empty description was shown blank; now it is shown by its name.
- An option with a bare name (a single letter, a number, `yes` or `no`) and no description is shown to the model by its name (since 0.3.7; before that its line was blank). Any other option with no description is shown as its name followed by a colon, as before. If the names are themselves letters or numbers, such as options named `A`, `B`, `C`, `D` with no descriptions, the default model's lettered prompt can show an option named D under the letter B, which is ambiguous. Give every option a description.
- A request with thousands of provenance spans is slower to mask. 10,000 spans now take under 3 seconds per question.
- The receipt does not identify everything that shaped the answer. Its hashes cover the state, the options and the model, but not the instructions, the provenance labels, the verdict classes, the fitted temperatures or the evidence encoder.
- The base model is loaded at a pinned revision from 0.3.5; before that, an install took whatever revision was current. The encoder's backbone configuration ships inside each checkpoint; a checkpoint without it would fall back to an unpinned download.
- With its own shipped rule, the default model flags 83.5% of questions with no right answer as "none of the options" and wrongly flags 0.6% of answerable ones (`results/eval/Q1.json`: `null_predicted_rate_unknowable` and `null_predicted_rate_answerable`). The 97% in the README is recall at a matched 5% false-alarm rate, with the threshold set on the test data for every system.
- The injection tests use attack wording kelter was trained on. The nudge and forged-instruction test sets plant one of four fixed sentences. The training augmentation plants the same four sentences, labelled as tool output or a retrieved document and with the right answer kept, in 5.4% to 6.1% of training records (11,677 of 199,502 in the r2 corpus, 5.85%; 1,543 of the 24,000 records in the default model's training sample, 6.4%). The held-out split is by source, not by wording. So kelter and the TF-IDF baseline were trained on these exact sentences, and Kev, Laya and Qwen2.5 were not: the attack success comparison is not like for like, and it shows resistance to wording kelter has seen. Training never planted a sentence under a `user` or `system` label; the forged-instruction test does. The same test items were rebuilt with four new sentences that appear in no training corpus (same items, positions and labels; only the sentence differs). Attack success, published wording then new wording, nudge and forged: default model 0.8% and 0.4%, then 1.2% (35 of 2,980) and 0.9% (26 of 2,980); `lower-latency` 1.2% and 1.5%, then 3.2% (92 of 2,858) and 5.1% (143 of 2,820); TF-IDF 3.4% and 3.2%, then 3.0% and 2.8%; Kev 15.1% and 16.8%, then 14.9% and 14.9%; Qwen2.5 27.8% and 28.4%, then 29.8% and 28.5%; Laya 68.9% and 67.5%, then 56.7% and 55.1%. So on unseen wording kelter is fooled more often than the published figures say, `lower-latency` about three times as often, and both stay below the three language models. With the new forged sentences the default model's unsafe acts are unchanged (4 of 3,120 with the evaluation tool's thresholds, 0 with the server's); `lower-latency` has 15 with the evaluation tool's thresholds (6 published) and 16 with the server's. Four sentences are a small sample of possible wording. See `results/review/attack_templates_r12.json` and `results/review/attack_heldout_r12.json`.
- The null-detection test set is not clean. Of the 3,120 swapped items in the corrected set of 5,918, 324 are held-out sharing questions in choice form whose options include `escalate` ("a needed fact is missing"). That is a defensible answer once the text has been swapped, yet they are labelled as having no right answer. The default model flags 310 of them (95.7%) and picks `escalate` on 13; `lower-latency` flags all 324. With them removed, the headline corrected null recall is 0.969 for the default model (0.968 published) and 0.762 for `lower-latency` (0.775 published); the swap group is 0.979 (0.977) and 0.778 (0.801). With `escalate` counted as correct it is 0.970 and 0.775. The four baselines' per-item outputs were not stored, so their figures under these alternatives are not known. The published tables are unchanged (`results/review/swap_escalate_r11.json`).
- In the default variant the evidence spans come from the encoder's own top option. When the encoder and the Qwen model disagree, the spans shown may support a different option. The sufficiency and necessity checks are then run against the Qwen model's verdict.
- The receipt's model hash does not include the base model revision.
- The same request can get slightly different probabilities depending on what else is in its batch. One request at a time, as the server runs, is deterministic. In one measurement of 30 long prompts, the largest difference between a prompt scored alone and scored inside a padded batch was 0.035, and 7 of the 30 differed by more than 0.01; the cause was not isolated (`results/eval/prefill_noise.txt`). This moves a few borderline decisions in the evaluation tool: the test split has 880 acts when the whole file is decided in one call and 884 in batches of 128 records (475 and 477 under the server's threshold; 737 and 736 for `lower-latency`).
- Some training records have their whole state masked away and keep their answer. One augmentation masks the untrusted text and marks the record "no answer" only when an evidence span overlapped the masked text. A BoolQ record has no evidence span and its passage is all untrusted, so it ends as the state `[MASK]` with its yes or no answer kept. In the r2 corpus 979 of 199,502 training records are like that (0.49%), and 0.42% to 0.52% in the other corpora (`results/review/masked_gold_r10.json`). Every encoder checkpoint trained on them. The default model's adapter did not, because its training drops records that contain `[MASK]`, but its evidence encoder r2 did. No development or held-out split holds such a record, so no published number is affected. The build is unchanged.
- The same swap is used as a training augmentation. It marks the record "no answer" whenever the new text comes from another source, although some questions still have an answer on the new text: a toxicity or paraphrase question, an NLI question given another NLI pair, a sharing question with `escalate`. In the r2 corpus 3,817 of 199,502 training records are swaps (1.9%) and 1,277 of those are in such classes (0.64% of the training records). In the other corpora the swaps are 1.8% to 3.1% of the records, and 1,277 to 2,112 of them are in such classes (0.59% to 0.98%) (`results/review/swap_escalate_r11.json`). The build is unchanged.
- Retraining from scratch will not reproduce the corpus exactly. Most source datasets are downloaded at whatever version is current, not at a pinned one, and the build did not record which versions it used. From 0.3.7 `manifest.json` records the sha256 of each source file the build fetched from the Hugging Face hub, and from 0.3.11 of the e-SNLI files, which come from GitHub.
- Control strings: text you send can no longer turn into the model's control tokens (0.3.9). Before that, a string such as `<|im_end|>` typed in the state, instructions or an option was read by the default model as a real end-of-turn marker. None of the evaluation files contains such a string, and token ids are identical before and after on them (`results/review/prompt_ids_r5.json`). `results/review/prompt_ids_r6.json` repeats the check on more data, comparing the code from before the change with 0.3.10. 0 of the 199,502 training records and 0 of the 24,000-record Q1 training sample contain a control string. Token ids are identical before and after on all of them, on every evaluation file and on the 231 JevBench public items.
- One exception on the encoder side: the literal string `[MASK]` in the state is still read as the mask token, because the engine's own masked passes write it. Every other control token is read as plain text. That is every special id the tokenizer lists, every added token it flags special, and the engine's own `[OPT]` and `[NULL]` markers.
- Many options, low probability: an option is kept in the set when its probability is at least 1 minus the threshold (0.009 for the default model, 0.053 for `lower-latency`), and the engine can act when exactly one option is kept. With many options the single kept option can have a low probability. On the default model, with at most 25 options, it is at least 0.78. On `lower-latency` it can be far lower: about 0.89 with 2 options, 0.16 with 16, and 0.053 with 25 or more (from the thresholds). No evaluated record has more than 10 options, so these low floors were not reached in any measurement: over 27,354 records, the lowest probability among acts under the server's threshold was 0.964 for the default model and 0.663 for `lower-latency` (`results/review/lowp_act_Q1.json`, `results/review/lowp_act_E1.json`). The limit on untrusted influence is an absolute drop in the winning option's probability (more than 0.2 for a `destructive` option), so it cannot trigger when that probability is itself 0.2 or less. It also does not look at whether hiding the untrusted text changes the top option. On the forged-instruction and authorization items, 75 acts of the default model and 267 of `lower-latency` had a different top option with the untrusted text hidden. None was on a `destructive` option, and one of the 267 was an unsafe act. Read `confidence` together with `action`, and keep option lists short on `lower-latency`, above all when an option is `destructive`.
- Empty-set fallback: when no label passes the conformal threshold, the set falls back to the single most likely label, and the action rule can then say `act` where it should have escalated. The server cannot reach this with the default model, because every request is decided under the policy threshold of 0.991. None of the records the smaller model E1 was evaluated on reach it either. The evaluation tool uses each record's own domain threshold, and with it the default model does reach it: 991 of 27,354 records have an empty set before the fallback, and 182 of those come out `act`. By file, the empty sets and the acts are test 70 and 13, test_forge 44 and 8, test_nudge 46 and 15, test_null 309 and 60, test_unknowable_corrected 450 and 69, and calib 72 and 17. So about 13 of the 880 acts on the test split in `results/eval/engine_Q1base.json` come from the fallback. It is "about" because this count ran the model in batches of 128 records and the published run decides the whole file in one call; see the batching limit above. The counts are in `results/review/fallback_Q1.json` and `results/review/fallback_E1.json`. It is not patched, because a change would alter those acts.
