# Limitations

Everything we know kelter does badly or have not tested, with the numbers.

## Limitations

- JevBench's hard tier is the weak spot: accuracy 0.568, and the model is overconfident there (mean top probability 0.657). The two padding and long-context training rounds tried so far did not improve it; they are recorded in `docs/results.md`.
- Null recall is reported on two test sets. The corrected set was defined after looking at test diagnostics; the original set gives 0.960.
- The action rule is conservative and its thresholds were not tuned, so it defers most held-out questions. Requests with no provenance tags are treated as one `unknown` segment: the engine can still act on ordinary options, but never on one marked `destructive`. It acts only when one option is left in the 95% set and the evidence is admissible: the spans give the same answer alone, masking them changes it, and their provenance is allowed for that kind of option. It defers when "none of the options" wins or no evidence is admissible, and escalates when the evidence is admissible but more than one option is left or untrusted text moved the answer too far. Treat `act` as a strong signal and `defer` as the default, not as a judgment that the answer is wrong. A looser rule that also acted on high confidence without evidence was tested and not shipped: it acted on 2,217 of 3,340 held-out questions at the same accuracy, but acted on planted text in 19 of 3,120 cases (`docs/results.md`).
- kelter trusts the provenance labels you supply. Text labelled `user` or `system` counts as trusted. Only options you mark `destructive` (in `verdict_classes`) are limited to user or system evidence and to a small budget of influence from untrusted text; other options can rest on tool output. So label text from tools, web pages, files and other models as `tool_output` or `retrieved_doc`, and mark every irreversible option `destructive`. When planted text naming a wrong option carries a trusted label, the default variant acts on the wrong option in 4 of 3,120 test cases and lower-latency in 6 of 3,120 (`results/eval/engine_Q1base.json`, `results/eval/engine_E1base.json`).
- The default variant needs a GPU. On a CPU the server runs it unquantized, and one answer took about eight minutes on a test machine (`results/e2e/2026-11-13.json`). The latency tool's int8 figure, 11.5 s for the four passes, is a measurement of a quantized copy that the server does not use. The lower-latency variant runs on a CPU: 6 to 44 s for two questions unquantized in our runs, and about 3 s per decision in the same int8 measurement.
- Calibration on JevBench's public tiers is worse than on our held-out data (ECE 0.038 to 0.124 by tier); the temperature was fitted on different kinds of text.
- Latency was measured on one laptop GPU shared with the desktop. The power mode of the earlier runs was noted by hand and is not stored in their results files; the balance-mode file records it. The figures in its highest power mode are the fastest it gets; in the balanced mode the default variant's decision takes 688 ms instead of 542 ms (`results/eval/latency_Q1_balance.json`). The lower-latency variant was measured in the highest mode only.
- The injection guarantee was tested on synthetic shell-gating and account-deletion items, not on real agent traces.
- The evidence spans come from the encoder, not from the Qwen model, so they show what the encoder relied on; the necessity check then measures whether masking them changes the Qwen model's answer (0.586 of e-SNLI answers change, against 0.362 for a random mask of the same size).
- JevBench's public tiers were used to choose between candidate models, each time under a rule written before the run (the default replaced the earlier ensemble partly on pooled public accuracy, 0.766 against 0.498). No public item was trained on, but the public-tier numbers are selected-on and should be read as optimistic. The sealed tier has never been seen.
- The server is stricter than the evaluation tool. Every request is given the `policy` type, so the engine uses the threshold fitted on policy questions (0.991) for all of them; the evaluation tool uses each test question's own type (0.455 to 0.991). Measured on the same held-out questions, the server's rule acts on 14% (475 of 3,340, all 475 correct) and escalates 15%; the evaluation tool's figures elsewhere in these documents are 26% and 3%. The `coverage_level` of 0.95 in an answer is therefore conservative for questions that are not policy questions (`results/eval/engine_Q1r1_policy.json`).
- `score` questions are not calibrated. The calibration data holds only `choice` and `noul` questions, so a score question is served at temperature 1 and its shortlist uses a threshold fitted on the other two types.
- Long inputs are cut. The default model reads at most 4,096 tokens of prompt; the encoder also keeps at most 96 tokens of the instructions and 48 tokens of each option. From 0.3.5 an answer reports a cut state in `verifier.truncated`. From 0.3.7 the same flag is also true when the encoder cut the instructions to 96 tokens or an option to 48 tokens. Earlier versions cut silently, and before 0.3.7 the flag did not cover the instruction and option cuts.
- An option named by a bare letter, a digit, "yes" or "no" is shown to the model by its description. Before 0.3.7 such an option with an empty description was shown blank; now it is shown by its name.
- The receipt does not identify everything that shaped the answer. Its hashes cover the state, the options and the model, but not the instructions, the provenance labels, the verdict classes, the fitted temperatures or the evidence encoder.
- The base model is loaded at a pinned revision from 0.3.5; before that, an install took whatever revision was current. The encoder's backbone configuration ships inside each checkpoint; a checkpoint without it would fall back to an unpinned download.
- With its own shipped rule, the default model flags 83.5% of questions with no right answer as "none of the options" and wrongly flags 0.6% of answerable ones (`results/eval/Q1.json`: `null_predicted_rate_unknowable` and `null_predicted_rate_answerable`). The 97% in the README is recall at a matched 5% false-alarm rate, with the threshold set on the test data for every system.
- In the default variant the evidence spans come from the encoder's own top option. When the encoder and the Qwen model disagree, the spans shown may support a different option. The sufficiency and necessity checks are then run against the Qwen model's verdict.
- The receipt's model hash does not include the base model revision.
- The same request can get slightly different probabilities depending on what else is in its batch. One request at a time, as the server runs, is deterministic. In one measurement of 30 long prompts, the largest difference between a prompt scored alone and scored inside a padded batch was 0.035, and 7 of the 30 differed by more than 0.01; the cause was not isolated (`results/eval/prefill_noise.txt`).
- Retraining from scratch will not reproduce the corpus exactly. Most source datasets are downloaded at whatever version is current, not at a pinned one, and the build did not record which versions it used. From 0.3.7 `manifest.json` records the sha256 of each source file the build read.
